# Рабочие инструменты Pinduoduo

Здесь сохранены установленные рабочие версии оператора: `pdd.py` управляет Android через ADB, `chat.py` работает с веб-чатами через отдельный профиль Chrome. Вспомогательные модули, шаблон сообщения, диагностические JAR и их исходники входят в комплект.

## Подготовка в Windows

1. Установите Python, Android SDK Platform Tools (ADB) и Google Chrome.
2. В каталоге `runtime` установите зависимости: `python -m pip install -r requirements.txt`.
3. Скопируйте `config.example.yaml` в `config.yaml` и при необходимости задайте расположение ADB и Chrome. Конфигурация локальная и исключена из Git. Профиль браузера всегда находится в `runtime/profile/`; параметра `profile_path` больше нет в примере, потому что код его не читал.
4. Подключайте Android только с разрешения владельца. Для входа в веб-чаты служит `python chat.py login`; данные входа остаются в локальной папке `profile/`.

`python pdd.py --help` и `python chat.py --help` показывают команды. Для ввода текста может потребоваться команда `install-adbkeyboard`: она отдельно скачивает сторонний APK и проверяет его по встроенному SHA-256 перед установкой. APK в репозитории нет.

**Ограничение жестов:** до независимой приёмки геометрии и защиты жестов `scroll`/`swipe` и длительное нажатие (`tap --long`, `tapel --long`, `tap_real(long_ms≠0)`) запрещены. В коде это исполняемая блокировка: команды отказывают до обращения к устройству, обхода через env/CLI/config нет. Чтение (`screen`, `ui`, `ui-diagnostic`, `ui-short-idle`) пассивно и никогда не нажимает на экран; для перекрытия мини-плеера есть отдельная явная команда `close-player`, которая срабатывает только при подтверждённом плеере и свежем полном дереве. Состояние телефона, сессии браузера, скриншоты и рабочие журналы в репозиторий не входят.

## Зависимости и поддерживаемые версии

- **Python.** Здесь проверено: Linux, Python 3.12.3. Python 3.10/3.11 и Windows не проверялись; не обещайте их поддержку без отдельного прогона.
- **`runtime/requirements.txt`.** Зафиксированы `Pillow==10.2.0`, `PyYAML==6.0.1`, `playwright==1.65.2`. Установка Pillow/PyYAML и импорт проверены в чистом виртуальном окружении на Python 3.12.3 (полный набор runtime-тестов зелёный); версия `playwright==1.65.2` сверена с PyPI, но установка playwright и живой браузер в этой среде не запускались.
- **`runtime/requirements-test.txt`.** Только `Pillow==10.2.0` и `PyYAML==6.0.1`. Офлайн-тесты подменяют браузер и не импортируют playwright; CI использует этот файл и не должен запускать `playwright install` (это скачало бы браузеры без необходимости).
- **Системные зависимости.** Для `pdd.py` нужен ADB (Android SDK Platform Tools) и телефон, подключённый с разрешения владельца. Для `chat.py` нужен Google Chrome и локальный профиль. Java/JDK и Android build-tools нужны только для пересборки диагностических JAR (`runtime/tools/`); для работы `pdd.py` уже собранные JAR не требуют Java на компьютере — они выполняются на телефоне через `app_process`.
- **Сеть.** Офлайн-тесты не ходят в сеть. `pdd.py install-adbkeyboard` отдельно скачивает APK, поэтому это действие требует сети и отдельного разрешения.

Для локальной проверки без телефона из корня репозитория используйте канонические команды из `AGENTS.md`:

```bash
python3 -m unittest discover -s runtime/tests -t runtime
python3 scripts/verify_versions.py
```

`scripts/verify_versions.py` запускает рабочую версию и кандидата раздельно и печатает конкретный проверяемый файл и каталог.

## Конкурентный доступ, геометрия и результат действия

- **Блокировка устройства.** Команды, меняющие состояние (`tap`, `tapel`, `close-player`, `text`, `key`/`back`/`home`, `launch`, `push-photo`, `install-adbkeyboard`), берут межпроцессную блокировку по серийному номеру. Чистое чтение (`screen`, `ui`, `status`, `current`, `ui-diagnostic`, `ui-short-idle`) её не берёт. Порядок фиксирован: сначала блокировка устройства, затем короткая блокировка состояния. На POSIX используется `flock` с дедлайном (ожидание не бесконечно), на Windows — `msvcrt` по тому же шаблону. После аварийного завершения процесса ОС снимает блокировку. Повторный вход из того же потока процесса разрешён; другой поток/процесс ждёт или получает явную ошибку по таймауту. Имя lock-файла санитизируется из серийного номера; при неизвестном серийном номере команда отказывает, общего lock на все устройства нет. Блокировка **не управляет внешней программой**, которая её игнорирует (прямой `adb`, другой инструмент): такие действия могут выполняться параллельно.
- **Геометрия.** Перед `tap`/`tapel`/`close-player`/`text`/`key` выполняется свежий `wm size`; при расхождении с кешем (поворот меняет местами w/h, сменилось разрешение) кеш инвалидируется, действие отменяется и требуется свежий `screen`/`ui`. Отсутствие или неразборчивость `wm size` — отказ. `capture()` сверяет размер PNG с кешем и при расхождении инвалидирует кеш и явно ошибается. Надёжного источника поворота на 180° среди используемых ADB-команд нет: ориентация выводится из соотношения w/h и размеров скриншота, поэтому поворот на 180° при тех же размерах этим не обнаруживается. Это ограничение не имитируется.
- **Результат действия.** `tap`/`tapel`/`text`/`key`/`launch`/`push-photo` возвращают `confirmation: command_sent`: команда отправлена, изменение состояния не подтверждено. `close-player` после нажатия повторно проверяет кадр: только фактическое отсутствие плеера даёт `confirmation: state_confirmed`; если плеер всё ещё виден или проверка не удалась — `result: unknown`, `confirmation: unknown`, без заявления «закрыт». При таймауте после отправки действие не повторяется вслепую: ошибка сообщает `unknown` (неизвестно, выполнено ли действие) и требует проверить `screen`/`ui`.

## Веб-чаты: черновик, CDP, конфигурация и вложения

- **Блокировка черновика.** `chat.py send` (а также `new`/`prepare`/`set-url`/`resolve`/`task`) берёт межпроцессную блокировку активного черновика провайдера на весь цикл: чтение контекста, проверки, вложения, текст, клик и фиксация состояния. Порядок фиксирован: сначала черновик/устройство, затем короткая блокировка состояния; обратный порядок запрещён. На POSIX используется `flock` с дедлайном, на Windows — `msvcrt`; при таймауте команда явно отказывает, после аварийного завершения владельца блокировку снимает ОС. Разные чаты блокируются независимо.
- **Неопределённая отправка.** Перед кликом сохраняется `pending_send`, снимок прежних флагов и `pending_context` (чат, время, стадия, `conversation_id`/`prepared_id`, имена запрошенных файлов, хеш текста). `task` не создаёт новую задачу и не стирает `pending_send`, пока оператор не проверит чат и не выполнит `resolve --reviewed-sent|--reviewed-not-sent`; повторная отправка того же черновика без разрешения запрещена. Автоматического повторного клика нет.
- **CDP и профиль.** Открытый TCP-порт не считается доказательством нужного браузера. Проверяются `/json/version` и `/json/list` по HTTP к `127.0.0.1`, строка `Browser` (Chrome/Chromium/HeadlessChrome), совпадение WebSocket-адреса с портом и привязка к профилю через файл `profile/DevToolsActivePort`, который Chrome пишет в `--user-data-dir`. Если порт занят чужим процессом или привязку к профилю подтвердить нельзя, `send`/`status`/`browser` явно отказывают. CDP не аутентифицирован: это проверка согласованности, а не криптографическое доказательство; локальный процесс теоретически может подделать ответ и файл профиля.
- **Конфигурация.** `save_config`/`update_config` пишут временный файл в каталоге конфигурации и выполняют `os.replace` под межпроцессной блокировкой; чтение-изменение-запись идёт только через `update_config` (так работают `pdd.py connect` и `chat.py primary`). Сбой до замены оставляет старый файл целым, временные файлы удаляются, содержимое конфигурации не выводится в сообщения об ошибках.
- **Вложения.** Состояние хранит стадии `requested → attachments_added → text_ready → send_started → sent_unknown → reply_received` (или `add_failed`/`text_failed`/`pre_send_failed`) и явный `delivery: unverified|unknown|not_sent`. Успешный вызов загрузки не означает доставку: без независимого подтверждения остаётся `unverified`/`unknown`. При частичном отказе добавления отправка не выполняется, файлы не объявляются доставленными, ошибка явная.
- **Завершение ответа.** Состояние генерации явное: `generating`, `finished`, `unknown`. `unknown` возвращается, если индикатор генерации не найден (устаревший селектор, страница не загрузилась), проверка недоступна или ожидание истекло. Только `finished` вместе с устойчивым текстом позволяет считать ответ полным; при `unknown` `read` пишет «может быть неполным», а `send` сохраняет `generation=unknown` и не заявляет полноту. Таймауты и ошибки не печатают хвост страницы или частичный текст.
- **Статус.** `chat.py status` пассивно читает только уже существующие контексты и вкладки. Он не вызывает `new_context`/`new_page`/`goto` (в том числе если подходящей вкладки нет) и не меняет URL; отсутствие вкладки — явный статус `NOT_OPEN`, а не повод её открыть. Подготовка/создание вкладок остаётся только у `new`/`prepare`/`send`.
- **Рекомендации Стратега.** `ACTION:` в ответе модели — недоверенное предложение, а не разрешение. `parse_action` ничего не исполняет, не вызывает устройство/браузер и не меняет конфигурацию; вывод помечает директиву `advisory_only: true`, `executed: false`, а при нескольких разных `ACTION` — `conflict: true`. Любое последующее действие по-прежнему требует отдельной проверки задачи, разрешения пользователя и актуального контекста; автоматической связи «ACTION → действие» нет.
- **Журналы и вывод.** По умолчанию `send` пишет только метаданные (`provider`, метод вложения, число файлов, `attachment_delivery=unverified`, `generation`, `content_saved=false`) и не печатает текст задачи/ответа. `task` и `status` выводят только длину/хеш задачи, а не её текст. `--show-content` явно выводит ответ в stdout; `--log-content` явно сохраняет в журнал полный исходящий текст (включая задачу и манифест) и полный ответ — такой журнал может содержать личные данные. Ошибки `send`/`read` не содержат текста задачи, ответа или хвоста страницы.
- **Имена журналов.** Журналы чатов создаются атомарно (`O_CREAT|O_EXCL`) с именем `<provider>_<UTC timestamp>_<random>.md`, например `gemini_20261114T083000Z_a1b2c3d4.md`. Параллельные процессы не перезаписывают друг друга, удаление среднего файла не приводит к переиспользованию имени. На POSIX новые журналы получают режим `0600`.

## Параметры `config.example.yaml`: где используются

Проверка сделана по коду (`runtime/pdd.py`, `runtime/chat.py`, `runtime/common.py`). Код не валидирует незнакомые ключи: опечатка в имени параметра молча игнорируется. Значения ниже — из отслеживаемого примера; рабочий `config.yaml` создаётся локально.

| Параметр | Где используется | Поведение и ограничения |
|---|---|---|
| `phone.serial` | `pdd.py::ensure_device`, `connect`, блокировки устройства | Пустая строка — автоматический выбор, только если подключено ровно одно устройство; иначе явная ошибка. Используется в имени lock-файла; при неизвестном серийном номере команда отказывает. |
| `phone.adb_path` | `pdd.py::run_adb` | Команда ADB; по умолчанию `adb`. Путь/имя не проверяется до запуска. |
| `phone.package` | `pdd.py`: проверки активного окна, фильтрация UI, `launch` | Ожидается `com.xunmeng.pinduoduo`; для части проверок иное значение даёт отказ, а не «похожее» приложение. |
| `phone.view_width` | `pdd.py::screen_info`, `cmd_screen` | Ширина координатной сетки `view`; по умолчанию 720. Должна быть положительным числом, иначе деление/масштаб дадут ошибку. |
| `phone.send_width` | `pdd.py::cmd_screen` | Ширина JPEG для отправки; по умолчанию 1080, ограничивается реальной шириной экрана. |
| `phone.pace_seconds` | `pdd.py::pace` | Ровно два числа `[a, b]` для `random.uniform(a, b)` между действиями. Длина/типы не валидируются заранее: неверное значение падает при использовании. |
| `browser.chrome_path` | `chat.py::chrome_path` | Явный путь к Chrome. Если пусто или файла нет — ищутся стандартные пути Windows, затем `NO_CHROME`. |
| `browser.cdp_port` | `chat.py`: `PORT`, TCP/HTTP-проба CDP | Локальный порт CDP; по умолчанию 9333. Проверяется привязка к профилю и WebSocket-адресу. |
| `browser.mode` | `chat.py::cmd_browser` | `headless` → `--headless=new`; `offscreen` → окно за пределами экрана; любое иное значение → видимое окно. Значение не ограничено списком. |

| `chats.primary` | `chat.py::cmd_send`, `status`, `task` и др. | Провайдер по умолчанию. Должен быть `gemini` или `chatgpt`; иначе `BAD_PROVIDER` при использовании. |
| `chats.<provider>.title` | `chat.py::build_manifest`, сообщения об ошибках | Отображаемое имя чата. |
| `chats.<provider>.host` | `chat.py::_valid_target` | Разрешённый HTTPS-host; URL с другим host отклоняется. |
| `chats.<provider>.url` | `chat.py::cmd_login`, `get_page`, `new` | Стартовый URL; должен соответствовать `host` и HTTPS. |
| `chats.<provider>.editor` | `chat.py`: `get_page`, `_empty_editor`, `put_text` | CSS-селектор(ы) редактора; используется первый найденный. |
| `chats.<provider>.send` | `chat.py::click_send` | Селектор кнопки отправки. |
| `chats.<provider>.stop` | `chat.py::generation_state` | Селектор индикатора генерации; отсутствие даёт `unknown`, а не «готово». |
| `chats.<provider>.assistant` | `chat.py::assistant_texts` | Селектор сообщений ассистента. |

Ключ удалён из `config.example.yaml`. `runtime/test_env.py` дополнительно удаляет его из синтетической копии, чтобы тестовая конфигурация не выглядела поддержкой несуществующей настройки. Не добавляйте его обратно, пока не реализовано чтение, валидация и тесты.

## Хранение, права доступа и очистка

- **Что создаётся локально.** `runtime/state.json` (задача, URL чатов, `pending_context`, имена файлов, хеши текста), `runtime/config.yaml`, `runtime/logs/` (снимки, журналы чатов, досье, `ui/latest.txt`, локальные JPEG из `push-photo`), `runtime/profile/` (профиль Chrome и сессии), lock-файлы `runtime/device-*.lock`, `runtime/draft-*.lock`, `runtime/config.yaml.lock`, `runtime/state.json.lock`, временные `.pdd-state-*.tmp`/`.pdd-config-*.tmp` и `runtime/tools/ADBKeyboard.apk`. Все эти пути, кроме самого кода, исключены в `.gitignore`; снимки, дампы и журналы не входят в Git.
- **`ui --no-log`.** Не записывает новую копию `latest.txt` и не удаляет прежнюю, но **сохраняет состояние для `tapel`** в `state.json` и создаёт временный дамп на телефоне. Это не обезличивание и не «ничего не сохранено».
- **Срок хранения и `clean`.** Срок задаётся вручную: `pdd.py clean --days N [--apply]` обрабатывает только `logs/screens`, `logs/chats`, `logs/dossiers`, `logs/ui`. Вне его области остаются: `state.json`, `config.yaml`, `profile/`, `tools/`, локальные JPEG `push-photo` прямо в `logs/` (не в подпапке), а также снимки `chat.py inspect --screenshot`, сохранённые в произвольный путь. Для них автоматической ротации нет; удалять их нужно отдельно с учётом личных данных. Автоматическое обезличивание не заявляется.
- **Права доступа.** Явный `chmod` применяется только к новым журналам чатов (`0600` на POSIX). Остальные файлы создаются с обычными правами процесса: на POSIX это зависит от `umask` (типично `0644` для файлов и `0755` для каталогов, то есть другие локальные пользователи могут читать), на Windows наследуются ACL родительского каталога. Держите `runtime/` в личном каталоге с ограниченным доступом и проверяйте ACL/права перед передачей машины или копии каталога.

## Проверки перед действием и остаточные риски

- **Координатный `tap`** проверяет активное окно Pinduoduo, получает свежее полное дерево, требует распознанную цель в точке, проверяет перекрытия и запрещённые элементы, затем повторно проверяет окно перед касанием. **Он не подтверждает идентичность карточки, магазина или SKU**, поэтому товарно-зависимые действия (`收藏`, удаление, выбор варианта) выполняйте через `tapel`, а не `tap`.
- **`tapel`** дополнительно сверяет сохранённые anchors страницы и идентичность самого элемента с новым полным деревом, а также отказывает при исчезновении, перемещении или неоднозначном совпадении цели. Сверка работает только по доступным идентификаторам (`goods_title`, `mall_name` и т.п.); если их нет, смена похожей карточки может остаться неразличимой.
- **`close-player`**, **`text`** и **`key`** имеют собственные проверки: свежий полный дамп, активное окно, подтверждённый фокус/плеер и (для `key del/search`) свежее поле ввода. Для всех клавиш, включая `back/home/recent`, требуется свежее полное дерево; при недоступном дампе команда отказывает.
- **Текст и секреты.** `pdd.py text` больше **не выводит введённый текст** (поле `text` удалено из JSON; остаётся `chars`). Код сопряжения и текст не попадают в собственные сообщения о таймауте: чувствительные вызовы `run_adb` помечены `sensitive`, значения дополнительно редактируются через `redact`. Это снижает риск утечки в stdout/исключения, но **не скрывает argv от ОС, adb-сервера, журналов устройства и системного аудита** — остаточное ограничение. `--clear` работает только с ADBKeyboard: после broadcast `ADB_CLEAR_TEXT` поле повторно читается через uiautomator, и при непустом `text` ввод отменяется до отправки. Проверка опирается на атрибут `text`; для полей, которые скрывают содержимое, она ограничена. Без ADBKeyboard `--clear` теперь **явно отклоняется до ввода** (надёжной очистки через `input` нет), а не игнорируется молча.
- **ADBKeyboard.** Совпадение имени пакета само по себе не доказывает подлинность. Репозиторий не содержит закреплённого сертификата/подписи, поэтому выдуманная проверка signer не вводится. Вместо этого установленный `base.apk` читается через `pm path`/`exec-out cat` и сверяется с уже закреплённым SHA-256 APK: `authentic`, `tampered` (ввод отказывает) или `unknown` (явное предупреждение в выводе, а не молчаливое доверие). Broadcast-сообщения ограничены пакетом `-p com.android.adbkeyboard`; точное имя receiver-компонента в репозитории отсутствует, поэтому это ограничение, а не доказанная защита от перехвата.
- **`push-photo`.** Локальный JPEG и файлы на телефоне получают уникальные имена (время + случайный суффикс); перед `push` проверяется отсутствие файла, уже существующие файлы не перезаписываются намеренно. Имена и папки валидируются (без разделителей и выхода из `/sdcard/DCIM/Camera`, `/sdcard/Pictures`). В выводе `remote` перечислены только пути, созданные текущим вызовом. `adb push` не умеет атомарный create-only: между проверкой и отправкой остаётся гонка, поэтому атомарная гарантия на устройстве не заявляется.
- **`clean`.** Отчёт различает `found`/`deleted`/`failed`, возвращает `status` (`dry_run`/`ok`/`partial`/`failed`) и `errors`; при частичном удалении `ok: false`. `--apply` не останавливается на первой ошибке. Обрабатываются только `logs/screens`, `logs/chats`, `logs/dossiers`, `logs/ui`; символические ссылки пропускаются целиком — цель ссылки и файлы вне разрешённой области не читаются и не удаляются. Без `--apply` отчёт содержит `would_delete` и ничего не удаляет.
- Проверки **уменьшают, но не устраняют** гонку TOCTOU между последней проверкой и касанием: Android может сменить окно, цель или перекрытие за это время. При любом сомнении действие нужно не выполнять; успешный ответ команды означает только отправленное касание, а не подтверждённый результат в интерфейсе.
- Жёсткие запреты (оплата, заказ, вступление в платную группу, массовый выбор, удаление) сохраняются; штучное удаление остаётся допустимым только по отдельному поручению для конкретной карточки, массовое — блокируется. Проверяются не только тексты, но и вложенные элементы/контейнеры и опасные зоны. Безымянный кликабельный слой в нижней панели карточки не считается безопасным **даже с `--force`**. Список запрещённых формулировок ограничен документированными в правилах/навыке и не является исчерпывающим классификатором: неразборчивую кнопку и неполное дерево безопасными не считать.
- В избранном `全选` и левая нижняя зона массового выбора блокируются. Один вызов `tapel` не может отметить несколько безымянных целей или работать в режиме `全选`: нажимайте по одной карточке. Выход команды не заявляет «сохранено/удалено»; удаление считается подтверждённым только после фактического исчезновения карточки из списка (процедурное требование, автоматической проверки в runtime нет).

## Ограничения сред: Windows, облако, CI

Наличие репозитория, навыков и даже зелёных офлайн-тестов **не означает**, что доступны телефон, ADB, Chrome, браузерный профиль, аккаунт или локальные сессии. Это нужно проверять отдельно на конкретной машине.

- **Проверено здесь.** Linux, Python 3.12.3, `flock`, синтетические ADB/UI/скриншоты/CDP-заглушки. На Linux проверены межпроцессные блокировки, таймауты и освобождение после аварийного завершения; симлинки в `clean` проверяются и пропускаются, если ОС не даёт их создать.
- **Windows не проверялась.** Ветка `msvcrt` (устройство, черновик, состояние, конфигурация), пути Windows, фактические ACL и `umask`, запуск Chrome, реальный ADB по Wi-Fi и реальный `uiautomator` остаются категорией (в). Тесты, которым нужен `fork`, явно пропускаются с причиной; тесты симлинков пропускаются, если среда не разрешает их создать. Это `skip`, а не ложный успех.
- **Облако/CI.** В облаке нет телефона, ADB, пользовательского Chrome, профиля и аккаунтов. Офлайн-тесты не должны ходить в сеть, запускать браузер или устройство. Межпроцессные блокировки действуют только в пределах одной машины/сеанса; `flock` не является распределённой блокировкой, а несколько CI-раннеров не должны делить одно устройство. Файловая система и права в конкретном облаке нужно проверять, а не предполагать.
- **CI-файл.** `.github/workflows/offline-tests.yml` добавлен для безопасных офлайн-проверок, но в этой среде GitHub Actions не запускался. Факт добавления файла не доказывает, что workflow выполнится на GitHub.

## Статус проверки

Категории не смешиваются:

- **(а) Проверено здесь (Linux, офлайн).** `python -m unittest` на Python 3.12 с замокированным ADB проверяет: `scroll`/`swipe` отказывают до устройства; `tap --long`, `tapel --long` и `tap_real(long_ms≠0)` отказывают до любого `run_adb`; обычный `tap_real(long_ms=0)` отправляет только `input tap`; чтение UI пассивно и не нажимает; `close-player` отказывает без подтверждённого плеера или свежего полного дерева и сообщает `unknown`, если после нажатия плеер не исчез; смена окна между проверкой и касанием, запрещённые контейнеры и безымянные слои в опасной зоне, `全选`/синоним, множественный `tapel` по чекбоксам, а также проверки `key del/search` дают отказ на синтетических данных. На Linux проверены: таймаут `_state_lock` (flock), взаимное исключение двух процессов по серийному номеру, освобождение блокировки ОС после `os._exit`, независимость разных серийных номеров, повторный вход в том же процессе; поворот/смена разрешения/отсутствие метрик и несовпадение размера PNG инвалидируют кеш; таймаут `tap_real` даёт одну отправку и `unknown`. Также офлайн проверены: отсутствие текста/base64 в JSON и ошибках `text`, отказ `--clear` без ADBKeyboard и проверяемая очистка с ним, редактирование argv в чувствительном таймауте; состояния клавиатуры `authentic`/`tampered`/`unknown`; уникальные имена и отказ от перезаписи в `push-photo`; `dry_run`/`ok`/`partial` и пропуск симлинков в `clean`. Для веб-чатов на Linux проверены: таймаут и освобождение ОС для `draft_lock`, независимость разных черновиков, сбой внутри цикла; `pending_send` и `pending_context` не стираются командой `task`, снимаются только `resolve` после явной проверки; частичный отказ вложений и сохранение `unverified`/`unknown`; параллельные `update_config` без потери обновлений, атомарная замена и сохранность старого файла при сбое; уникальные журналы чатов после удаления среднего файла и при одновременной записи из двух процессов; отсутствие текста задачи/ответа в stdout и журнале без opt-in; неизменность `CFG` при разборе `ACTION`. CDP-проба и три состояния генерации (`generating`/`finished`/`unknown`) проверены заглушками страницы и селекторов; пассивность `status` (без `new_page`/`new_context`/`goto`) — заглушкой контекста.
- **(б) Смоделировано заглушками.** Ответы ADB, дампы UI, скриншоты, `dumpsys`, `pm path` и содержимое установленного APK в тестах синтетические. Для `chat.py` заглушками проверены HTTP/TCP-ответы CDP, файл `DevToolsActivePort`, браузерная страница, селекторы индикатора генерации и часы ожидания, пассивный `status`, вложения и состояние черновика. Это проверяет логику ветвей, но не поведение Android, Chrome и реальных веб-чатов.
- **(в) Остаётся проверить на Windows и реальном телефоне/браузере.** Блокировки `msvcrt` (устройство, черновик, конфигурация), реальный ADB по Wi-Fi, реальный `uiautomator`, фактическая геометрия и ориентация экрана, поведение реального мини-плеера, фактические прокрутка/свайп и долгое нажатие. Отдельно: реальный Chrome с `--user-data-dir` и `--remote-debugging-port`, наличие и формат `DevToolsActivePort` в разных версиях Chrome, поведение CDP `/json/version` и `/json/list` при старте и перезапуске, фактическая отправка/доставка вложений и ответы веб-чатов. В реальном браузере нужно проверить, остаётся ли элемент `stop` в DOM после завершения генерации: если провайдер удаляет его из DOM, состояние будет `unknown` до обновления селекторов. Также: реальная очистка/ротация `logs/` и `profile/`, фактические ACL Windows и `umask` на целевой машине. Чтение установленного APK и совместимость `pm path`/`exec-out cat` на разных прошивках, фактическая работа `ADB_CLEAR_TEXT` и `-p com.android.adbkeyboard`, возможный перехват broadcast (гипотеза до проверки на конкретном Android/APK), реальные гонки `adb push` и поведение `clean` на файловых системах устройства/Windows.

Зелёные офлайн-тесты подтверждают только протестированное поведение в синтетической среде. Они **не снимают запрет на реальные жесты** (`scroll`, `swipe`, длительное нажатие) и **не подтверждают безопасность на телефоне**; запрет остаётся до отдельной приёмки.

Более новый экспериментальный вариант `pdd.py` от 13 ноября 2026 года доступен в `runtime/experimental/pdd-02d1f/` вместе с тестами и пояснениями. Он **не принят** в рабочую версию и проверяется отдельно командой `python3 scripts/verify_versions.py`; обоснования для продвижения сейчас нет.
